# GesGROW Design System

## 1. Propósito

El GesGROW Design System define los principios visuales, de interacción y de experiencia que deben compartir todas las interfaces del ecosistema GesGROW.

Su objetivo es asegurar que cada producto, módulo y superficie se sienta parte de una misma plataforma, aunque responda a contextos de uso diferentes.

Actualmente GesGROW se compone principalmente de:

- Portal Web de Gestión
- Aplicación de Campo
- futuros módulos operativos y administrativos

El Design System debe permitir que estas interfaces compartan identidad sin obligarlas a comportarse exactamente igual.

---

## 2. Qué es GesGROW

GesGROW es una plataforma digital para la gestión de operaciones agrícolas.

Su propósito es conectar la operación de campo con la gestión administrativa, productiva y analítica de una empresa agrícola.

GesGROW debe transmitir:

- tecnología;
- agricultura;
- innovación;
- cercanía;
- modernidad;
- confianza;
- calidad;
- control.

La experiencia debe sentirse profesional y de alto valor, sin perder claridad ni utilidad operacional.

---

## 3. Personalidad de marca

GesGROW debe sentirse como una plataforma:

- tecnológica;
- agrícola;
- moderna;
- innovadora;
- cercana;
- confiable;
- robusta;
- premium.

La calidad visual debe transmitir que se trata de un producto bien construido, serio y preparado para operaciones reales.

### Idea central

> GesGROW debe sentirse como una plataforma agri-tech premium: moderna, elegante, útil y claramente agrícola.

La interfaz debe mostrar que la agricultura forma parte de la identidad del producto, no solamente de su contenido.

---

## 4. Dirección visual

La dirección visual de GesGROW combina:

- tecnología moderna;
- identidad agrícola visible;
- precisión operativa;
- diseño premium;
- simplicidad de uso;
- alto nivel de acabado.

La agricultura puede aparecer mediante:

- color;
- iconografía;
- nomenclatura;
- fotografía o ilustración contextual;
- visualización de cultivos, fundos, parcelas o producción;
- patrones gráficos sutiles.

Debe evitarse convertir la identidad agrícola en decoración excesiva.

### Principio

> Agrícola sí. Decorativo no.

---

## 5. Sensación esperada

GesGROW debe sentirse:

- limpio;
- moderno;
- tecnológico;
- estructurado;
- eficiente;
- profesional;
- confiable;
- visualmente cuidado;
- fácil de comprender;
- claramente agrícola.

El producto debe aspirar a una calidad visual comparable con software SaaS moderno de alto nivel, manteniendo una identidad propia y relacionada con el entorno agrícola.

---

## 6. Lo que GesGROW no debe ser

GesGROW no debe sentirse como:

- una plantilla SaaS genérica;
- un ERP antiguo;
- un sistema corporativo frío;
- una interfaz excesivamente técnica;
- una colección de tarjetas sin jerarquía;
- una aplicación agrícola infantil;
- una web decorativa sin intención operacional;
- un dashboard sobrecargado;
- un producto visualmente inconsistente entre módulos.

También deben evitarse:

- gradientes decorativos sin función;
- glassmorphism excesivo;
- iconografía inconsistente;
- demasiados colores simultáneos;
- sombras agresivas;
- animaciones largas;
- elementos puramente ornamentales que resten claridad.

GesGROW no posee una única interfaz.

El Design System debe soportar distintos contextos de uso.

Actualmente existen dos superficies principales:

### Portal Web de Gestión

Pensado para:

- administración;
- planificación;
- configuración;
- consultas;
- reportes;
- análisis;
- seguimiento operativo;
- gestión de usuarios;
- estructura agrícola;
- campañas;
- personal;
- cosecha;
- suscripciones.

Contexto principal:

- escritorio;
- laptop;
- tablet;
- mouse;
- teclado;
- sesiones más largas;
- alta densidad de información.

---

### Aplicación de Campo

Pensada para:

- operación agrícola;
- escaneo;
- asignación;
- registro;
- control de cosecha;
- uso en PDA;
- conectividad intermitente;
- operación repetitiva.

Contexto principal:

- PDA Android;
- teléfono;
- lector físico de códigos;
- uso táctil;
- exteriores;
- alta luminosidad;
- conectividad irregular;

## 8. Una marca, dos modos de uso

Portal y Aplicación de Campo deben sentirse como interfaces hermanas, no como copias.

Comparten:

- marca;
- paleta;
- tipografía;
- iconografía;
- estados semánticos;
- microcopy;
- principios de accesibilidad;
- lenguaje visual general.

Pero adaptan:

- densidad;
- tamaño de controles;
- navegación;
- layouts;
- interacción;
- nivel de información;
- motion;
- comportamiento responsive.

## 10. Principios globales

### 10.1. Claridad antes que decoración

Toda decisión visual debe ayudar a comprender:

- qué está ocurriendo;
- qué información importa;
- qué puede hacer el usuario.

La estética nunca debe reducir la legibilidad.

---

### 10.2. Simplicidad de uso, riqueza de diseño

GesGROW debe ser simple de utilizar sin sentirse visualmente básico.

> Simple no significa pobre.

La interacción puede ser sencilla mientras el acabado visual permanece cuidado y premium.

---

### 10.3. Jerarquía evidente

Cada pantalla debe dejar claro:

1. dónde está el usuario;
2. qué información es principal;
3. qué acción puede realizar;
4. qué estado tiene el sistema.

---

### 10.4. Agricultura como identidad

La naturaleza agrícola del producto debe percibirse de forma consistente.

No debe depender únicamente de textos como “Campaña” o “Cosecha”.

La identidad agrícola también debe expresarse mediante:

- verdes;
- amarillos de cosecha;
- iconografía;
- lenguaje;
- datos;
- imágenes cuando correspondan;
- estructuras espaciales y productivas.

---

### 10.5. Diseño para operaciones reales

GesGROW no es una demostración visual.

Los componentes deben soportar:

- errores;
- estados vacíos;
- carga;
- offline;
- permisos;
- datos largos;
- grandes volúmenes;
- usuarios reales;
- uso repetitivo.

---

### 10.6. Consistencia sin rigidez

Los productos comparten foundations y componentes base.

Sin embargo, cada superficie puede tener variantes específicas cuando el contexto lo requiera.

Ejemplo:

```text
Button
├── Portal
└── Field
```

La coherencia no implica utilizar exactamente las mismas dimensiones en todos los dispositivos.

---

### 10.7. Datos primero
GesGROW es una plataforma operativa y analítica.

Los datos deben poder comprenderse con rapidez mediante:
- jerarquía;
- tablas;
- métricas;
- rankings;
- gráficas;
- filtros;
- estados;
- comparaciones.

La visualización de datos forma parte del lenguaje principal del producto.

---

### 10.8. Accesibilidad como requisito
La accesibilidad no debe tratarse como mejora opcional.

Debe considerarse desde el diseño de:
- color;
- contraste;
- focus;
- formularios;
- iconografía;
- navegación;
- estados;
- componentes interactivos.

---

## 11. Identidad cromática
La identidad principal de GesGROW utiliza:
### Verde
Representa:
- agricultura;
- crecimiento;
- producción;
- estabilidad;
- naturaleza;
- confianza.

Es el color principal de la marca.

### Amarillo cosecha
Representa:
- producción;
- energía;
- cosecha;
- atención;
- actividad.

Debe utilizarse como acento.

No debe competir con el verde principal.

### Neutros
Los fondos, bordes y textos utilizan una familia de neutros ligeramente cálidos.

Esto evita que GesGROW se sienta excesivamente frío o tecnológico.

---

## 12. Modos de color

### Portal
Debe soportar:

```text
Light Mode
Dark Mode
```

Ambos modos deben diseñarse como temas completos.

Dark mode no debe ser simplemente una inversión automática de colores.

### Aplicación de Campo
Debe utilizar:
```text
Light Mode
```

como modo único inicialmente.

La prioridad es:
- legibilidad;
- alto contraste;
- visibilidad bajo luz natural;
- consistencia operacional.

---

## 13. Tipografía
La familia tipográfica principal es:
```text
Inter
```

GesGROW necesita una tipografía:
- moderna;
- altamente legible;
- clara en números;
- eficiente en tablas;
- consistente en dispositivos pequeños;
- adecuada para interfaces densas.

Los datos numéricos tienen especial importancia dentro del sistema.

---

## 14. Iconografía
La iconografía debe ser:
- moderna;
- simple;
- reconocible;
- consistente;
- de grosor uniforme;
- compatible con interfaces densas.

La agricultura puede representarse mediante iconos específicos cuando ayuden a comprender el dominio.

Ejemplos:
- planta;
- parcela;
- fundo;
- caja de cosecha;
- ticket;
- trabajador;
- maquinaria;
- riego;
- inventario.

Evitar:
- emojis como iconografía final;
- estilos mezclados;
- iconos 3D;
- ilustraciones infantiles.

---

## 15. Movimiento
El motion forma parte de la percepción premium del Portal.

Debe utilizarse para:
- comunicar cambios;
- facilitar orientación;
- mejorar feedback;
- reforzar jerarquía.

Debe ser:
- breve;
- suave;
- natural;
- funcional.

Ejemplos:
- expansión del sidebar;
- hover;
- cambios de estado;
- apertura de paneles;
- aparición de información;
- cambios entre vistas.

Nunca debe retrasar una operación.

---

## 16. Sidebar del Portal
El Portal utiliza una navegación lateral persistente en desktop.

Características deseadas:
- apariencia clara;
- estética premium;
- efecto glass sutil;
- bordes suaves;
- profundidad visual ligera;
- iconografía consistente.

Comportamiento:

```text
sin interacción
→ sidebar compacto
→ solo iconos

hover / focus
→ expansión
→ icono + texto
```

La transición debe ser suave y rápida.

En dispositivos donde hover no exista, el comportamiento debe adaptarse.

En tablet o móvil puede convertirse en:
- drawer;
- panel temporal;
- navegación responsive equivalente.

---

## 17. Glass
GesGROW puede utilizar efectos glass de manera controlada.

Permitido:
- blur sutil;
- transparencia ligera;
- bordes suaves;
- superficies elevadas;
- overlays.

Evitar:
- fondos excesivamente transparentes;
- múltiples capas glass;
- texto sobre superficies poco legibles;
- efecto visual dominante.

### Principio
> Glass es un detalle, no la identidad.

---

## 18. Visualización de datos
La visualización de datos tiene importancia alta en GesGROW.

El Design System debe soportar:
- KPIs;
- tendencias;
- rankings;
- barras;
- líneas;
- comparaciones;
- producción diaria;
- rendimiento;
- campañas;
- lotes;
- personal;
- futuros módulos.

Todas las visualizaciones deben contar con una alternativa legible en tabla cuando sea necesario.

Los gráficos deben priorizar interpretación antes que decoración.

---

## 19. Escalabilidad del producto
El Design System no debe diseñarse únicamente para Harvest.

Debe poder extenderse a futuros módulos como:
- Inventario;
- Maquinaria;
- Riego;
- Calidad;
- Costos;
- Trazabilidad;
- Mantenimiento;
- Logística;
- Analítica avanzada.

Los componentes base deben ser neutrales al dominio cuando sea posible.

Evitar nombres como:

```text
HarvestPrimaryButton
```

cuando el concepto real es:

```text
PrimaryButton
```

Las especializaciones deben existir solo cuando exista una necesidad real.

## 21. Fuente de verdad
La documentación del Design System es la fuente conceptual de verdad.

Los tokens y componentes de producción deben mantener correspondencia con ella.

A futuro la relación esperada es:

```text
Design System Docs
        ↓
Design Tokens
        ↓
Component Library
       ↙ ↘
 Portal  Field App
```

La implementación no debe introducir valores visuales arbitrarios cuando ya exista un token equivalente.

---

## 22. Tokens compartidos
Los foundations deben evolucionar hacia tokens reutilizables.

Ejemplo:

```text
color.brand.*
color.harvest.*
color.surface.*
color.text.*
color.border.*

space.*
radius.*
shadow.*
motion.*
font.*
```

Los tokens pueden tener modos específicos:

```text
theme.light
theme.dark

density.portal
density.field
```

cuando corresponda.

---

## 23. Componentes compartidos
Los componentes base pueden poseer variantes según superficie.

Ejemplo:

```text
Button
├── primary
├── secondary
├── danger
├── ghost
├── field
└── portal
```

La variante debe responder a diferencias reales de interacción.

No deben crearse componentes duplicados solo por pertenecer a aplicaciones distintas.

---

## 24. Microcopy
La voz de GesGROW debe ser:
- clara;
- profesional;
- cercana;
- directa;
- breve;
- útil.

Debe evitar:
- lenguaje técnico innecesario;
- mensajes impersonales;
- códigos de error expuestos;
- frases ambiguas.

Los errores deben explicar:
1. qué pasó;
2. qué puede hacer el usuario.

---

## 25. Estados del producto
Todo componente que dependa de datos debe considerar cuando corresponda:

```text
default
hover
focus
pressed
selected
loading
success
warning
error
disabled
empty
offline
pending
```

No debe diseñarse únicamente el caso ideal.

## 26. Responsive
GesGROW debe adaptarse al contexto, no simplemente reducir el tamaño.

Portal

Prioridad:

```text
Desktop
→ Tablet
→ Mobile
```

Field App

Prioridad:

```text
PDA
→ Mobile
→ Tablet
```

La arquitectura responsive puede ser distinta entre ambas superficies.

---

## 27. Accesibilidad
Como mínimo:
- contraste adecuado;
- navegación por teclado en Portal;
- focus visible;
- labels accesibles;
- targets táctiles adecuados;
- estados no comunicados solo mediante color;
- textos legibles;
- tablas correctamente estructuradas;
- gráficos acompañados por datos accesibles.

---

## 28. Calidad visual
Una pantalla GesGROW debe sentirse terminada.

Debe evitarse introducir interfaces que sean funcionales pero visualmente incompletas.

Una pantalla debe revisar:
- jerarquía;
- alineación;
- espaciado;
- ritmo;
- color;
- estados;
- responsive;
- empty state;
- loading;
- error;
- accesibilidad;
- microinteracciones.

---

## 29. Criterios de aprobación globales
Antes de considerar terminada una nueva interfaz debe responder sí a estas preguntas:
1. ¿Se reconoce como parte de GesGROW?
2. ¿La jerarquía es evidente?
3. ¿La interfaz se siente moderna?
4. ¿Existe una identidad agrícola visible?
5. ¿Es fácil encontrar la acción principal?
6. ¿La información importante tiene prioridad?
7. ¿Los estados están diseñados?
8. ¿Utiliza los tokens oficiales?
9. ¿Reutiliza componentes existentes?
10. ¿Es accesible?
11. ¿Funciona correctamente en su dispositivo objetivo?
12. ¿Tiene un acabado visual de producto premium?
30. Principio final

GesGROW debe lograr un equilibrio entre dos necesidades:

```text
Operaciones reales
+
Producto digital premium
```

No debe sacrificarse utilidad por estética.

Tampoco debe utilizarse la funcionalidad como excusa para una interfaz visualmente pobre.

El resultado esperado es:

> Una plataforma agrícola profesional, moderna y confiable que se sienta construida específicamente para su industria y no adaptada desde una plantilla genérica.
